# eg2-l2v1 — EG2 Hybrid W4 저메모리 런타임 (v0.2.0, B200 전용)

**v0.2.0 에는 vLLM 플러그인 `eg2q` 가 들어 있습니다. 이 플러그인으로 ThakiCloud 의 EmbeddingGemma 2 하이브리드 W4 모델([`ThakiCloud/eg2-hybrid-w4-media`](https://huggingface.co/ThakiCloud/eg2-hybrid-w4-media))을 수정하지 않은 업스트림 vLLM 에 올려, OpenAI 호환 `/v1/embeddings` API 로 텍스트·이미지·오디오·비디오 임베딩을 서빙할 수 있습니다. 공개된 4비트 체크포인트를 그대로 쓰며 재양자화도, 새 체크포인트도, vLLM 포크도 없습니다. NVIDIA B200 한 장에서 같은 vLLM 경로로 띄운 BF16 참조보다 가중치 상주 GPU 메모리가 43.7% 적고, 처리량은 참조의 0.826배 이상을 유지했습니다. 빨라지는 도구가 아니며 네이티브 INT4 GEMM 도 아닙니다.**

이 저장소에는 **코드만** 있습니다. 모델 가중치와 평가 데이터는 다시 배포하지 않습니다. 두 런타임 모두 공개 체크포인트를 고정 revision 으로 내려받아 그대로 쓰고, 모델·모델 카드·공식 로더(`eg2_quant.py`)는 손대지 않습니다.

| 경로 | 내용 | 도입 |
|---|---|---|
| [`vllm/`](./vllm) | `eg2q` vLLM 플러그인, 서버 스크립트, 예제, 셀프테스트 | **v0.2.0** |
| 저장소 루트 | sentence-transformers 런타임 `eg2_l2v1` (변경 없음) | v0.1.0 |

두 경로는 PyTorch 빌드가 다릅니다. vLLM 경로는 vLLM 휠이 끌어오는 2.13.0+cu130 이고 루트 런타임은 2.11.0+cu130 이라서, 환경을 따로 만들어 설치해야 합니다.

## vLLM 플러그인 (`vllm/`, v0.2.0 신규)

### 동작 방식

플러그인은 vLLM 의 표준 확장 지점인 `vllm.general_plugins` 엔트리 포인트로 `eg2q` 라는 양자화 설정을 등록합니다. 체크포인트는 비전·오디오 타워의 Linear 247개를 4비트 코드와 fp16 scale·zero-point(그룹 64)로 저장합니다. 플러그인은 레이어 종류로 짐작하지 않고 체크포인트 헤더를 읽어 정확히 이 247개를 고릅니다. 이 레이어들은 4비트 코드 상태로 GPU 에 남아 있다가, forward 를 부를 때마다 해당 레이어만 BF16 으로 풀린 뒤 평범한 BF16 GEMM 에 들어갑니다. 언어 모델과 BF16 투영 같은 나머지 Linear 는 vLLM 의 비양자화 경로를 그대로 탑니다. vLLM 의 다른 부분은 고치지 않습니다.

### 실측 (NVIDIA B200 ×1)

참조 팔은 같은 체크포인트를 공식 로더로 한 번 BF16 으로 복원한 뒤, 같은 vLLM 빌드와 같은 엔진 설정으로 띄운 것입니다. 플러그인 팔은 4비트 체크포인트를 `eg2q` 로 띄운 것입니다. 환경은 vLLM `0.31.1rc1.dev48+ga8260cbc5`(커밋 `a8260cb` 업스트림 nightly 휠), torch 2.13.0+cu130, transformers 5.19.0, 모델 revision `bc3574a285a2779ac0686cc149342f30fbbf8f5b` 입니다. 아래 기준은 모두 측정 전에 등록했고 결과를 본 뒤 바꾸지 않았습니다.

| 항목 | 결과 | 기준 |
|---|---|---|
| 체크포인트 키로 적재된 4비트 레이어 | **247 / 247** (비전 113 · 오디오 134), 언어 모델 Linear 146개는 BF16 유지 | 247개 전부 |
| 복원 가중치와 공식 로더 비교 | sha256 기준 247개 전부 **비트 동일** | 비트 동일 |
| 가중치 상주 GPU 메모리 (vLLM "Model loading took") | **0.80 GiB**, 참조 1.42 GiB → **0.563배 (−43.7%)** | 0.70배 이하 |
| 로딩 직후 GPU 메모리 (프로세스 전체) | 1,842 MiB, 참조 2,412 MiB | 기록만 |
| 참조 대비 처리량, 유효 3회 중 최저 셀 | **0.826배** (오디오, batch 64) | batch 16·64 모두 0.80배 이상 |
| 참조 대비 정확도 | 플러그인×참조 모든 쌍에서 min cos **1.0** (아래 설명) | 0.99999 이상 |
| OpenAI 호환 서빙 | 텍스트·이미지·오디오·비디오 단건 성공, 동시 요청 **32 / 32** 성공(16개 병렬), 서버도 247개를 플러그인으로 적재 | 네 모달리티 전부 |

참조 대비 처리량입니다. 유효 3회의 중앙값이고 괄호 안은 최솟값입니다.

| 모달리티 | batch 16 | batch 64 |
|---|---|---|
| text | 0.993 (0.987) | 0.998 (0.995) |
| image | 0.932 (0.923) | 0.992 (0.941) |
| audio | 1.082 (0.898) | 1.040 (**0.826**) |
| video | 1.007 (0.994) | 0.989 (0.961) |

같은 회차에 BF16 끼리 비교한 대조 비율이 모든 셀에서 0.90~1.10 안에 들어야 그 회차를 유효로 봤습니다. 5회 중 3회가 유효했고, 나머지 2회는 사전에 정한 이 규칙에 따라 버렸습니다. 1.0 을 넘는 값은 대조군 잡음 범위 안에 있으므로 **빨라졌다는 뜻이 아닙니다.** 플러그인은 복원 단계를 하나 더 거친 뒤 같은 BF16 GEMM 을 돌립니다.

**메모리 수치에 대해.** −43.7% 는 로드 후 vLLM 이 보고하는 가중치 상주 메모리입니다. 서버 전체 VRAM 이 그만큼 줄어든다는 뜻은 아닙니다. vLLM 은 `--gpu-memory-utilization` 한도까지 활성값과 캐시용 메모리를 미리 잡기 때문에, 서버가 차지하는 양은 가중치가 아니라 이 설정이 정합니다.

### 정확도 결과가 보여 주는 것과 보여 주지 않는 것

*입증한 것:* 같은 vLLM 실행 경로에서 4비트 가중치를 상주시키는 방식이 BF16 복원 참조 대비 사전등록한 정확도 기준을 충족합니다. 모달리티마다 32개, 모두 128개 항목을 플러그인 3회와 참조 3회로 임베딩했습니다. 네 모달리티 모두 플러그인×참조 9쌍의 min cos 이 표시 정밀도에서 1.0 이었고, 기준은 0.99999 였습니다. 참조를 3회 더 돌린 음성 대조도 통과했습니다. 4비트 레이어에만 ±2⁻⁸ 상대 오차를 일부러 넣은 양성 대조는 이미지·오디오·비디오에서 검출됐습니다. 텍스트가 움직이지 않은 것은 예상한 결과입니다. 언어 모델은 양자화되지 않아서 넣은 오차가 텍스트 경로에 닿지 않습니다.

*아직 입증하지 못한 것:* 플러그인이 어떤 실행 조건에서든 정확히 같은 출력을 낸다는 보장은 하지 못합니다. 참조 자신도 프로세스가 바뀌면 출력이 비트 단위로 같지 않습니다. 128개 중 4개(텍스트 2, 비디오 2)는 플러그인과 참조의 차이가 참조 6회 사이에서 관측한 최대 변동보다 조금 컸습니다. 크기는 float32 마지막 자릿수 수준(성분 최대 절대 차이 7.3 × 10⁻⁸ 이하, 1 − cos ≈ 10⁻¹⁵)이지만 반올림해 지우지 않고 여기 적습니다. 앞선 진단 실행에서는 3.85초 오디오 한 항목에서 참조끼리도 간헐적으로 흔들렸습니다(참조 실행 사이 cos 0.99978 까지). 이번 측정에서는 재현되지 않았는데, 관측되지 않았다는 뜻일 뿐 해결됐다는 뜻은 아닙니다.

### 설치

Linux x86_64, Python 3.12, CUDA 13.0 을 지원하는 NVIDIA 드라이버가 필요합니다. 새 환경에서 설치하십시오.

```bash
git clone https://github.com/ThakiCloud/eg2-l2v1.git && cd eg2-l2v1
sudo apt-get install -y gcc g++ libgl1 libglib2.0-0 ffmpeg     # Triton 런처 빌드, OpenCV, 디코더
bash vllm/install.sh          # 잠금 의존성을 --no-deps 로(vLLM 은 커밋 a8260cb 휠), eg2q 플러그인, pip check
python vllm/selftest_vllm.py --out vllm_result.json            # exit 0 이면 통과 (B200 에서 약 10분)
```

`vllm/requirements.lock.txt` 는 `vllm/requirements.in` 을 공개 인덱스(PyPI, `wheels.vllm.ai/<commit>`, `download.pytorch.org/whl/cu130`)에서만 해석해 만들었습니다. vLLM 은 커밋 `a8260cbc5c020d250b3964141cde8fd839152714` 의 업스트림 nightly 휠 인덱스에서 설치합니다. 언젠가 그 인덱스가 정리되면 같은 커밋을 소스에서 빌드하면 됩니다.

### 서빙

```bash
bash vllm/serve.sh            # 고정 revision 을 내려받고 EG2Q_CKPT 를 설정한 뒤 :8000 에서 API 서버를 띄웁니다
python vllm/client_example.py --url http://127.0.0.1:8000 --image cat.png --audio clip.wav --video clip.mp4
```

`serve.sh` 는 검증할 때와 같은 인자로 `python -m vllm.entrypoints.openai.api_server` 를 실행합니다(`--runner pooling --dtype bfloat16 --max-model-len 8192 --quantization eg2q`, Matryoshka 차원 768/512/256/128, `audio_seq_length=750`). 플러그인은 `EG2Q_CKPT` 가 모델로 넘긴 것과 같은 로컬 체크포인트 디렉터리를 가리켜야 하며, `serve.sh` 가 이 값을 설정합니다. 요청 형식은 [README.md](./README.md#serve) 와 같습니다. 오디오는 16 kHz 모노로 넣고, 30초보다 긴 클립은 모델 처리기가 30초로 자릅니다. `vllm.LLM` 으로 프로세스 안에서 쓰는 방법은 [`vllm/offline_example.py`](./vllm/offline_example.py) 에 있습니다.

### 셀프테스트

`vllm/selftest_vllm.py` 는 검증한 revision 의 체크포인트를 내려받아 다음을 모두 계산으로 확인합니다. 체크포인트 형식과 4비트 레이어 247개, 오프라인 `vllm.LLM` 이 247개를 전부 플러그인으로 적재하는지, 엔진이 복원한 BF16 가중치가 체크포인트의 공식 `eg2_quant.py` 와 sha256 으로 같은지, 네 모달리티 임베딩이 768차원·유한·단위 노름인지, `serve.sh` 로 띄운 서버가 모달리티별 단건 요청과 동시 요청 32개를 처리하는지입니다. 이때 vLLM 이 보고한 가중치 메모리도 기록합니다. GPU 없이 도는 CPU 단위 시험(`pytest vllm/tests`)은 플러그인의 복원 결과를 공식 로더와 비교합니다.

### 독립 설치 검증 (공개 소스만 사용)

사내 레지스트리·오브젝트 스토리지·공유 디렉터리에 접근할 수 없는 깨끗한 NVIDIA B200 컨테이너에서 위 설치 절차를 그대로 실행했습니다. 공개 베이스 이미지 `python:3.12-slim-bookworm` 에 Debian 시스템 패키지를 깔고, `requirements.in` 을 공개 인덱스에서 해석해 커밋된 잠금 파일을 만들었습니다(199개: PyPI 177, pypi.nvidia.com 15, download.pytorch.org 6, vLLM 은 wheels.vllm.ai). 이어서 `vllm/install.sh` 를 실행했고 `pip check` 는 깨끗했습니다. 마지막으로 Hugging Face 에서 체크포인트를 받아 `vllm/selftest_vllm.py` 를 돌렸습니다.

## sentence-transformers 런타임 (저장소 루트, v0.1.0 이후 변경 없음)

[`ThakiCloud/eg2-hybrid-w4-media`](https://huggingface.co/ThakiCloud/eg2-hybrid-w4-media)의 4비트 미디어 가중치를 sentence-transformers 안에서도 4비트로 유지하는 로더입니다. GPU 상주 메모리는 BF16 모델의 0.58배이고, 임베딩은 공식 로더와 비트 단위로 같습니다. 대신 빨라지지는 않습니다. 실제 녹음에서 오디오 처리량은 BF16 의 0.83~0.94배입니다. 공식 로더는 모델을 불러올 때 4비트 비전·오디오 Linear 를 전부 BF16 으로 풀어 두지만, 이 런타임은 4비트 코드를 GPU 에 둔 채 Linear 를 부를 때마다 그 가중치만 풀어 BF16 행렬곱에 넣습니다.

### 실측 (NVIDIA B200 ×1)

환경은 torch 2.11.0+cu130, transformers 5.19.0, sentence-transformers 6.1.0, 드라이버 580.65.06, 모델 revision `bc3574a285a2779ac0686cc149342f30fbbf8f5b` 입니다. 처리량은 같은 프로세스에서 BF16 과 번갈아 3회 잰 중앙값입니다.

| 항목 | 값 |
|---|---|
| 로드 후 GPU 상주 메모리 | **0.874 GB** (BF16 1.502 GB 대비 **0.582배**) |
| 로딩 중 최대 GPU 메모리 | **1.797 GB** — 배포할 때는 이만큼 여유를 잡아야 합니다 |
| 공식 로더 대비 정확도 | 합성 입력 min cos ≥ 0.9999998 · 실제 오디오 비트 동일 |

합성 입력(3초 오디오), 잠금 파일로 설치한 환경에서 BF16 대비 처리량입니다.

| 모달리티 | batch 16 | batch 64 |
|---|---|---|
| text | 1.014 | 1.002 |
| image | 0.956 | 0.988 |
| audio | **0.825** (회차 0.816 · 0.843 · 0.825) | 0.875 |
| video | 0.989 | 0.998 |

실제 녹음(FSD50K dev, 44.1 kHz 를 16 kHz 로 재표본화, 구간당 64개)에서 BF16 대비 처리량입니다.

| 길이 | batch 16 | batch 64 |
|---|---|---|
| 4초 이하 | 0.831 | 0.908 |
| 7~12초 | 0.884 | 0.960 |
| 27~30초 | 0.944 | 0.984 |
| 30초 초과(처리기가 30초로 자름) | 0.944 | 0.984 |

짧은 오디오가 가장 불리합니다. forward 중 활성값 메모리는 BF16 과 같습니다(예: 30초 클립 64개에 6.2 GB 추가).

공개 이미지(`python:3.12-slim-bookworm`)에 PyTorch 공식 인덱스의 휠과 잠금 파일만 설치하고 모델을 Hugging Face 에서 직접 받은 환경에서도 결과가 같았습니다. selftest 는 네 모달리티 모두 비트 단위로 일치했고, 상주 메모리는 0.874 GB(BF16 의 0.582배)였습니다. 오디오 batch 16 처리량은 BF16 의 0.822배(회차 0.832 · 0.822 · 0.861)로 측정됐습니다.

### 설치

```bash
git clone https://github.com/ThakiCloud/eg2-l2v1.git && cd eg2-l2v1
bash install.sh
python selftest.py --out result.json     # exit 0 이면 통과
```

`install.sh` 는 PyTorch 공식 인덱스에서 `torch==2.11.0+cu130` 과 `torchvision==0.26.0+cu130` 을 설치하고, `requirements.lock.txt` 를 `--no-deps` 로 설치해 pip 가 torch 를 바꾸지 못하게 한 뒤 `pip check` 를 돌립니다. torchvision 이 꼭 필요한 이유는 transformers 5.19 가 EmbeddingGemma 2 의 이미지·비디오 전처리에 그것을 쓰기 때문입니다.

### 사용법

오디오는 16 kHz 모노 float32 로 넣습니다. 30초보다 긴 클립은 모델 처리기가 30초로 자릅니다. 코드 예시는 [README.md](./README.md#usage) 와 같습니다.

## 지원 범위 (두 경로 공통)

- **검증한 GPU 는 NVIDIA B200(SM 10.0) 하나뿐입니다.** 다른 GPU 지원은 주장하지 않습니다. 루트 런타임의 경우 H200 이 중앙값으로는 기준을 넘었지만 3회 중 1회가 audio@16 0.796 이어서 지원 목록에 넣지 않았습니다.
- **메모리 수치는 가중치 상주 메모리 기준입니다.** 서버 전체 VRAM 절감률과 다릅니다(위 "메모리 수치에 대해" 참고).
- **BF16 보다 빨라졌다는 주장이 아닙니다.** 두 경로 모두 복원한 뒤 같은 BF16 GEMM 을 돌리며 네이티브 INT4 커널은 없습니다. GPU 메모리가 제약이 아니라면 BF16 가중치가 같거나 더 빠릅니다.
- **정확도 비교 기준은 같은 vLLM 경로에서 4비트를 BF16 으로 복원한 참조입니다**(루트 런타임은 공식 로더). 다른 서빙 스택과 비교한 결과가 아닙니다.
- **미해결 과제(G1):** 이미지·오디오 입력에서 vLLM 과 sentence-transformers 파이프라인의 임베딩이 같다는 것은 BF16 모델에서도 아직 입증되지 않았습니다. 이번 릴리스는 이 문제를 해결하지 않습니다. 두 스택의 벡터를 확인 없이 한 인덱스에 섞지 마십시오.
- 고정 revision 의 4비트 체크포인트 `ThakiCloud/eg2-hybrid-w4-media` 전용이며 CPU 경로는 없습니다.
- 이 저장소는 모델 가중치와 평가 데이터를 배포하지 않습니다.
